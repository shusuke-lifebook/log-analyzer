# Checkout API 障害分析レポート

## 1. 概要

- 対象日時: 2026-03-20 10:00:00-10:25:00 UTC
- 対象機能: `POST /api/checkout`
- checkout 件数: 6件
- 成功: 2件、失敗: 4件
- 失敗率: 66.7%
- 影響: 10:10 UTC 以降の checkout がすべて HTTP 502
- `POST /api/chat` は確認範囲内で全件 HTTP 200

## 2. 分析方法

1. LBログから HTTP 502 を抽出した。
2. APログから WARN と ERROR を抽出した。
3. `traceId` をキーに両ログを突合した。
4. 正常な依存先ログと比較して、障害箇所を切り分けた。

## 3. 観測事実

### リクエスト結果

| 時刻 UTC | トレース ID | 結果 | 所要時間 | payment-service の状況 |
|---|---|---:|---:|---|
| 10:00 | `trace001` | 200 | 3,120 ms | timeout 1回後に成功 |
| 10:05 | `trace002` | 200 | 4,184 ms | timeout 2回後に成功 |
| 10:10 | `trace003` | 502 | 3,988 ms | timeout 2回後も timeout |
| 10:15 | `trace004` | 502 | 4,021 ms | timeout 2回後に `ECONNRESET` |
| 10:20 | `trace005` | 502 | 2,870 ms | 1回 timeout 後に到達不能 |
| 10:25 | `trace006` | 502 | 1,918 ms | 到達不能 |

LBログで抽出した 4件の HTTP 502 は、すべて上表の `trace003`-`trace006` と一致した。各 trace ID は APログで `payment-service` の ERROR と、続く `web-service` の 502 エラーに対応している。

### 正常性が確認できる範囲

- LLM API: `trace001`-`trace006` で HTTP 200、約791-915 ms
- PostgreSQL: 全件でクエリ完了、約11-15 ms、各1行
- ロードバランサーの結果はアプリケーションログと一致
- checkout の失敗は 10:10、10:15、10:20、10:25 と5分間隔で継続

## 4. 想定原因

### 第一候補: payment API の障害またはネットワーク経路障害

決済呼び出しだけが timeout、`ECONNRESET`、到達不能の順に悪化し、最終的にアプリケーションが 502 を返しています。LLM と DB は正常であるため、アプリケーション全体やロードバランサーの障害よりも、決済 API 自体、接続先、DNS、ファイアウォール、NAT/プロキシなど決済経路に限定された障害の可能性が高いです。

### 第二候補: payment API のレート制限、障害、または接続プール枯渇

外部決済事業者側のレート制限・部分障害、または payment-service 側の HTTP 接続プール枯渇でも同様の症状が発生します。現ログだけでは、接続拒否・名前解決失敗・TLS 失敗・HTTP 5xx を区別できません。

### 可能性が低い原因

- PostgreSQL 障害: クエリ成功、低レイテンシのため可能性は低い
- LLM API 障害: 全トレースで応答成功のため可能性は低い
- ロードバランサー単独の障害: upstream のアプリケーションログでも同じ 502 を確認できるため可能性は低い
- checkout の入力データ不備: 時刻を境に一律に発生しており、決済 API エラーの内容とも一致しない

## 5. 推奨する切り分け

1. `trace003`-`trace006` を使い、payment-service の詳細ログ、HTTP ステータス、宛先ホスト、DNS/TLS エラー、接続時間、応答時間を確認する。
2. 決済事業者のステータスページ、障害通知、レート制限、利用量メトリクスを 10:00-10:30 UTC で照合する。
3. payment-service 実行環境から決済 API への DNS、TCP/TLS、プロキシ/NAT、ファイアウォールの疎通を確認する。
4. payment-service の接続プール使用率、ソケット数、ファイルディスクリプタ、CPU、メモリ、再起動履歴を確認する。
5. 10:10 UTC 前後のデプロイ、設定変更、証明書更新、ネットワーク変更の有無を確認する。
6. 決済 API の監視で、timeout、接続リセット、到達不能を別々のメトリクスとして集計する。

## 6. 対策

### 即時対応

- 決済事業者またはネットワーク側の障害が確認できるまで、checkout の再試行を無制限に増やさない。
- checkout を「決済処理中」として安全に再開できる設計がある場合は、同期失敗を非同期リトライへ切り替える。
- 決済 API の冪等キーを必ず利用し、timeout 後の再試行による二重請求を防止する。
- 502 の発生率と payment API の失敗分類にアラートを設定し、担当者へ通知する。
- 影響時間帯の注文について、決済事業者側の取引状態と内部注文状態を照合する。

### 恒久対策

- timeout を接続、TLS、応答に分け、リトライは指数バックオフとジッター付きで上限回数を設ける。
- `timeout`、`ECONNRESET`、`unreachable`、相手側 HTTP 5xx を区別して記録する。
- サーキットブレーカーと bulkhead を導入し、決済 API 障害が他機能へ波及しないようにする。
- 接続プールの上限・アイドル時間・keep-alive を決済 API の仕様と負荷に合わせて見直す。
- 外部依存先のヘルスチェック、合成監視、依存先別の SLI/SLO を整備する。
- 取引状態照会 API または照合ジョブを用意し、応答不明状態を自動回復できるようにする。

## 7. 結論

本ログからは、10:10 UTC 頃に決済 API への通信が不安定化し、10:20 UTC 以降は到達不能となったことが最も強く示唆されます。原因の確定には payment-service の詳細なネットワークエラーと、決済事業者・ネットワーク設備のメトリクス照合が必要です。現時点の優先順位は、決済経路の疎通確認、依存先障害確認、二重請求防止を伴うリトライ制御の確認です。

## 8. 分析上の制約

- アプリケーションログは checkout 6件分のみで、payment-service の宛先、HTTP ステータス、DNS/TLS 詳細は含まれていない。
- ロードバランサーログにリクエストサイズ、upstream 時間、接続エラー、再試行情報がない。
- 障害開始前後のデプロイ履歴、メトリクス、決済事業者の障害情報は未確認である。
